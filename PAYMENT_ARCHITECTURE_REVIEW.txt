PAYMENT ARCHITECTURE REVIEW — Checkout, Gateway, and Order Insertion Audit
Project: e-co custom PHP MVC (Paymob gateway: online_card, online_wallet, plus COD)
Date: 2026-10-12
Type: Diagnostic only. No patch code included.

================================================================
1. CURRENT WORKFLOW ANALYSIS (as implemented today)
================================================================
Step 1 — Checkout submit (Js payment.js orderBtn.onclick):
  Collects address plus cart from localStorage, POSTs to checkout
  process endpoint with CSRF header.
Step 2 — Order insertion (CheckoutController::process):
  Revalidates stock per item against products.quantity, recomputes
  prices server-side, then INSERTs one row into orders with
  payment_status = pending and transaction_id = NULL for every
  payment method, COD included.
Step 3 — Stock deduction happens immediately at insert time via
  Product::deductStock for every item, before any money moves.
Step 4 — Branch by method:
  COD returns redirect to my-orders. Order is final at this point.
  Online returns redirect to payment pay route with order_id.
Step 5 — Gateway handoff (PaymentController::pay):
  Authenticates to gateway, creates gateway order with
  merchant_order_id = localId plus timestamp, builds a payment key,
  redirects the shopper to the hosted iframe or wallet deep link.
  Guard exists against paying an already-paid order.
Step 6a — Server webhook (PaymentController::callback, HMAC verified):
  Success sets payment_status = paid plus gateway transaction id.
  Failure sets payment_status = failed, order status = cancelled,
  and restocks items with a double-restock guard.
Step 6b — Browser return (PaymentController::response):
  Reads a success flag from the return URL query string and renders
  a success or failure page. Display only. Clears local cart on
  the success branch. Writes nothing to the database.
Step 7 — Admin operations (AdminOrderController::update):
  Status changes restock or re-deduct inventory based on a keyword
  list. Marking any order complete force-marks payment_status = paid
  even when it was never paid.

================================================================
2. TRANSACTION ID BUG — WHY THE FIELD SHOWS EMPTY
================================================================
Root cause, insertion side:
  Order::create receives transaction_id = null on every checkout
  (CheckoutController payload sets it null unconditionally), so
  every newborn row has an empty transaction id by construction.
Why COD stays empty forever:
  No later step ever assigns one. COD has no gateway event, and no
  internal reference generator exists. The value remains NULL for
  the whole order lifetime.
Why online can also stay empty:
  The only writer is the success branch of the gateway webhook. Any
  order that never receives a verified success callback (abandoned
  session, failed attempt, expired payment key, webhook URL not
  registered or unreachable in the gateway dashboard, HMAC mismatch)
  keeps NULL permanently.
Why admin shows dashes:
  The admin orders view reads data-trx-id from transaction_id with an
  empty fallback and renders dashes when empty. The customer invoice
  masks the same gap with a hash-plus-id fallback, so the two screens
  disagree: invoice shows a pseudo-reference while admin shows blank.
Correct handling, COD vs online:
  COD must receive a deterministic internal reference at insert time
  (derived from the final order id plus date marker), never NULL, so
  every row carries a traceable reference from birth.
  Online must keep transaction_id NULL only while awaiting payment,
  then store the gateway transaction id exclusively from the verified
  server webhook, never from browser parameters. Display layers must
  share one fallback rule instead of two divergent ones.

================================================================
3. GHOST ORDERS BUG — WHY FAILED PAYMENTS CREATE VALID ORDERS
================================================================
Primary flaw, creation sequence:
  The order row is created as a fully valid pending order BEFORE the
  shopper ever reaches the gateway, and inventory is deducted at the
  same moment. Payment outcome is therefore decoupled from order
  existence: a failed OTP, a wrong card, a closed browser tab, or an
  expired wallet link all leave behind a real order row with reduced
  stock and no failure marker.
Missing and weak reconciliation:
  The browser return page trusts a query-string success flag and
  performs zero database writes, so it cannot cancel, expire, or
  correct anything. It is cosmetic only, and its success branch
  clears the shopper cart on an unverified signal.
  The webhook is the only component that can mark failure, but it
  fires only if the gateway is configured to call it, the URL is
  publicly reachable, and HMAC verification passes. There is no
  polling fallback, no verification-on-return via gateway lookup,
  and no expiry sweeper for rows stuck in pending. One missed webhook
  equals one permanent ghost order with permanently held stock.
Indistinguishability in admin:
  A failed online order and a legitimate COD order look identical in
  the orders list (both pending, both uncancelled), so staff cannot
  tell ghosts from real demand, and revenue queries inherit the noise.
Masking behavior:
  Completing such an order in admin silently flips payment_status to
  paid without any gateway evidence, which converts ghosts into fake
  revenue instead of surfacing the underlying gap.

================================================================
4. COMMERCIAL STANDARD SOLUTION (production-ready pattern)
================================================================
Principle: never create a fulfillable order before money is confirmed.
Introduce an explicit awaiting-payment state and treat the gateway
webhook as the sole source of truth, with the browser return used
only for UX after server-side verification.
A. Order state machine:
  COD path keeps current behavior (insert as confirmed demand with an
  internal reference), because cash collection happens offline.
  Online path inserts with a dedicated state meaning awaiting payment
  plus an expiry timestamp (for example 30 minutes), visibly distinct
  from COD pending in admin filters and excluded from revenue and
  demand metrics until paid.
B. Inventory handling:
  Either reserve without deducting until the paid webhook arrives, or
  keep immediate deduction paired with a scheduled reaper that
  restocks and cancels expired awaiting-payment rows. The reaper must
  reuse the existing idempotency guard so a late webhook arriving
  after expiry cannot double-restock or resurrect the order.
C. Webhook reconciliation hardening:
  Enforce a uniqueness constraint on the gateway transaction id and
  record every webhook event (success and failure) in an event log
  before mutating order state, making redeliveries safe.
  On browser return, ignore the query-string flag and perform a
  server-side gateway lookup by merchant order id, then render the
  page from database state. Add a manual admin verify-and-sync action
  per order for stuck rows.
D. Identity and idempotency:
  Keep the existing double-submit guard and timestamped merchant
  order id, and additionally store a per-checkout idempotency key so
  retries and back-button resubmits collapse onto one intent row.
E. Admin and reporting separation:
  Ghost and expired rows must be filterable and excluded from KPI
  queries by rule (paid non-cancelled only, plus completed COD),
  and completing an unpaid online order must be blocked or gated
  behind explicit confirmation instead of silently marking paid.
F. Suggested rollout order:
  Internal references for COD first, then awaiting-payment state plus
  reaper, then verify-on-return, then event log with unique
  transaction constraint, then admin filters and KPI rule alignment.
